## 1. 目标与核心原则

当前 `src/` 只有 `main.rs` + 空 `page/` + 空 `utils/`，所有窗口、侧边栏、主题逻辑都堆在 `main.rs`（约 230 行），难以维护。本规划书定义**清晰的模块边界与依赖方向**，让后续页面和功能可以按需扩展而不互相污染。

核心分层原则（自上而下，依赖只允许指向下层 / 同层展示件）：

| 原则 | 说明 |
| --- | --- |
| **展示与逻辑分离** | `page/` 只负责"长什么样、摆哪里"；"做什么、算什么"一律在 `utils/`。 |
| **`utils/` 不依赖 GTK** | `utils/` 模块禁止 `use gtk` / `use adw` / `use glib`，即不持有任何控件引用。这样 `utils` 可被 `cargo test` 直接单测（无需显示器）。 |
| **单向依赖** | 依赖方向严格：`main → app/window/navigation → page → (widgets + utils + model)`；`utils → model`；下层永不直接引用上层。 |
| **页面不直接改全局状态** | 页面通过调用 `utils` 提供的函数 / 把事件回调转发给上层来完成"处理事情"，自身只做组装与展示。 |
| **可组合** | 公共的复合控件抽到 `widgets/`，页面只做拼装，避免重复代码。 |

## 2. 目录结构（目标态）

```
linbox/
├── Cargo.toml
├── Cargo.lock
├── docs/
│   ├── UI_SPEC.md            # 已有：界面视觉/交互/动画规范
│   └── 项目结构规划书.md      # 本文件
├── resources/                # 非代码资源（如需要）
│   ├── icons/                # 应用图标、自定义符号图标（遵循 §7 图标规范）
│   └── gresources/           # 若后续引入 .ui / gtk-builder 资源
└── src/
    ├── main.rs               # 入口：创建 adw::Application，绑定 activate
    ├── app.rs                # 应用级：全局样式/主题初始化、资源加载、单例状态
    ├── window.rs             # 主窗口外壳：ToolbarView + HeaderBar + 内容布局
    ├── navigation.rs         # 侧边栏 + 路由：注册/切换页面、汉堡按钮联动
    ├── page/                 # 【展示层 · 仅 UI】
    │   ├── mod.rs            # 汇总各页面，导出注册入口
    │   ├── home.rs           # 首页
    │   ├── settings.rs       # 设置页（PreferencesPage 风格）
    │   └── <其他页面>.rs      # 按 sidebar 条目逐一新增
    ├── widgets/              # 【展示层 · 可复用复合控件】
    │   └── mod.rs            # 如：卡片行、空状态封装、自定义列表项
    ├── utils/                # 【逻辑层 · 处理实现】
    │   ├── mod.rs            # 汇总导出
    │   ├── config.rs         # 配置读写 / 持久化（gio::Settings 或文件）
    │   ├── theme.rs          # 主题模式切换（跟随/浅/深）
    │   ├── toast.rs          # 全局通知封装（供页面调用）
    │   └── <业务模块>.rs      # 如 project / favorite / message 等真实功能逻辑
    └── model/                # 【数据层 · 纯数据结构】
        └── mod.rs            # 数据模型定义（struct/enum）、与 utils 配合完成业务
```

> 注：`page/`、`utils/`、`model/`、`widgets/` 各自在 `mod.rs` 中用 `mod xxx;` 暴露子模块，并在 `main.rs`/`lib` 中按需 `pub use`，保持顶层清晰。

## 3. 各模块职责说明

### 3.1 `main.rs`（入口）
- 仅做最小工作：构建 `adw::Application`、注册 `activate` → 调用 `app::run` / `window::build`。
- **不放任何 UI 构建代码**，把"应用如何启动"与"窗口长什么样"解耦。

### 3.2 `app.rs`（应用级）
- 应用启动时的一次性初始化：加载 `resources/`、设置 `StyleManager` 默认（跟随系统）、注册全局快捷键/动作。
- 持有需要跨页面共享的单例状态（如当前用户、全局配置句柄），通过 `utils::config` 读取。

### 3.3 `window.rs`（窗口外壳）
- 构建 `AdwApplicationWindow` + `ToolbarView` + `HeaderBar`（标题、汉堡按钮、主题菜单按钮、搜索入口）。
- 组合 `navigation` 提供的「侧边栏 + 内容 Stack」，组装成完整窗口。
- **不做具体页面的内容**，只提供"内容区插槽"。

### 3.4 `navigation.rs`（导航 / 路由）
- 维护左侧 `ListBox` 侧边栏条目与右侧 `gtk::Stack` 页面的映射（即现有 `add_nav_item` 的归宿）。
- 提供 `register_page(name, icon, label, widget)` 供各页面注册；处理条目点击 → `stack.set_visible_child_name`、汉堡按钮联动 `OverlaySplitView::set_show_sidebar`。
- 是 `page` 与 `window` 之间的"接线员"。

### 3.5 `page/`（展示层 · 仅 UI）【你原始构想的核心】
- 每个文件 = 一个页面，导出形如 `pub fn build() -> impl IsA<gtk::Widget>` 的纯 UI 构建函数（或 `pub struct XxxPage { ... }` 持有内部 widget 句柄）。
- **只负责**：声明式地搭建控件树、设置样式类（`title-1`、`card` 等）、把控件引用留在结构体里。
- **不负责**：任何计算、IO、状态变更。需要"做事"时，调用 `utils` 的函数，或把按钮的 `connect_*` 回调转发到上层/导航层去触发 `utils`。
- 例：`home.rs` 只画首页布局；点击"刷新"按钮时，回调里调用 `utils::project::fetch_list()`（返回数据），再把结果填充回页面控件。

### 3.6 `widgets/`（展示层 · 复用控件）
- 跨页面复用的复合控件（如统一的"项目卡片行"、"空状态页封装"、"带图标的设置行"）。
- 仍是纯展示件，可调用 `utils` 做轻量格式化，但不持有业务状态。

### 3.7 `utils/`（逻辑层 · 处理实现）【你原始构想的核心】
- 所有"处理事情"的实现：配置读写、网络/文件 IO、数据计算、业务规则。
- **硬性约束**：不 `use gtk/adw/glib`，不接收/保存 `&Widget`。输入是数据（或参数），输出是数据（`Result<T, E>` / `Option<T>`）。
- 页面 / 导航层拿到返回值后自行更新 UI。
- 例：`theme.rs` 提供 `set_scheme(sm, scheme)` 与 `Scheme` 枚举；`config.rs` 提供 `load()` / `save()`。

### 3.8 `model/`（数据层）
- 纯 `struct`/`enum` 数据定义（如 `Project`、`Message`、`AppConfig`），可 `derive(Clone, Debug, Serialize, ...)`。
- 不依赖任何 UI 框架；`utils` 读写 `model`，`page` 展示 `model`。

## 4. 依赖方向图（必须守住）

```
        main.rs
           │
           ▼
      app.rs / window.rs / navigation.rs
           │                         │
           └──────────┬──────────────┘
                      ▼
                 page/  (仅展示)
                  │   │
        ┌─────────┘   └─────────┐
        ▼                       ▼
   widgets/                  utils/  (逻辑, 无 GTK)
        │                       │
        └─────────┬─────────────┘
                  ▼
              model/  (纯数据)
```

禁止的箭头（会出现环或破坏可测性）：
- ❌ `utils/` 引用 `page/` 或 `gtk`/`adw`。
- ❌ `page/` 直接修改全局应用状态而不经 `utils`。
- ❌ `model/` 引用任何上层。
- ❌ `navigation.rs` 在内部实现业务逻辑（只做路由/接线）。

## 5. 一个完整的页面示例（page ↔ utils 协作）

以"首页"为例，说明展示层如何调用逻辑层：

```rust
// ===== src/utils/project.rs（逻辑层，无 GTK）=====
pub struct Project { pub id: u32, pub name: String }

/// 拉取项目列表（实际可换成文件/网络/数据库）
pub fn fetch_list() -> Result<Vec<Project>, String> {
    // ... 真实处理逻辑，不碰任何控件 ...
    Ok(vec![Project { id: 1, name: "示例项目".into() }])
}
```

```rust
// ===== src/page/home.rs（展示层，仅 UI）=====
use gtk::prelude::*;
use crate::utils::project;

pub struct HomePage {
    root: adw::StatusPage,   // 暂用占位，真实页面换成 Box/ListBox
    list: gtk::ListBox,
}

pub fn build() -> HomePage {
    let root = adw::StatusPage::new();
    let list = gtk::ListBox::new();

    // 展示层只负责"把数据画出来"，数据来自 utils
    match project::fetch_list() {
        Ok(items) => {
            for it in items {
                let row = gtk::Label::new(Some(&it.name));
                list.append(&row);
            }
            root.set_child(Some(&list));
        }
        Err(e) => root.set_description(Some(&format!("加载失败：{e}"))),
    }

    HomePage { root, list }
}

impl HomePage {
    pub fn widget(&self) -> &impl IsA<gtk::Widget> { &self.root }
}
```

要点：**`page` 调用 `utils::project::fetch_list()` 拿数据，自己负责渲染**；`utils` 完全不知道有 `HomePage` 存在，因此可独立单测。

## 6. 命名与代码约定

| 项 | 约定 |
| --- | --- |
| 页面模块 | 与 sidebar 条目一一对应，文件名小写蛇形（`home.rs`、`settings.rs`） |
| 页面构建 | 统一导出 `pub fn build() -> XxxPage`，`XxxPage` 提供 `widget()` 取根控件 |
| 逻辑模块 | 按业务域拆分（`config`/`theme`/`project`/`message`），文件名小写蛇形 |
| 数据模型 | 类型用 PascalCase（`Project`/`AppConfig`），放 `model/` |
| 模块汇总 | 各目录 `mod.rs` 内 `pub mod xxx;` 并视情况 `pub use` |
| 信号连接 | 优先 `glib::clone!(#[weak] ...)` 防内存泄漏（沿用现有写法） |

## 7. 从当前代码迁移的步骤

1. **抽出外壳**：把 `main.rs` 中的 `build_ui` 拆为 `window.rs`（窗口/HeaderBar/ToolbarView）与 `navigation.rs`（`add_nav_item` + `OverlaySplitView` 接线）；`apply_scheme_animated` 移入 `utils/theme.rs`（注意：动画函数本身用 GTK，故放 `app.rs` 或 `window.rs` 更合适，theme 枚举与切换判断放 `utils`）。
2. **落地 `page/`**：新建 `page/home.rs`、`page/settings.rs`，各自 `build()` 返回现有 `StatusPage` 占位；`navigation.rs` 改为调用 `page::home::build().widget()` 注册。
3. **落地 `utils/`**：把主题切换的判断/枚举抽到 `utils/theme.rs`；预留 `config.rs` 作为后续配置持久化入口。
4. **接入 `model/`**：当某个页面需要真实数据时，先定义 `model`，再写对应 `utils` 处理逻辑。
5. **瘦身 `main.rs`**：最终 `main.rs` 仅保留 `Application` 创建与 `activate` 绑定。

## 8. 验收清单

- [ ] `main.rs` 不再包含 UI 构建代码，仅创建 `Application`。
- [ ] 每个页面独立成 `page/<name>.rs`，且不含业务逻辑 / IO。
- [ ] `utils/` 下任意模块 `grep` 不到 `use gtk` / `use adw` / `use glib`（动画相关除外，但应集中并注明）。
- [ ] 新增一个页面只需：写 `page/xxx.rs` + 在 `navigation.rs` 注册一行，无需改动 `window`/`utils`。
- [ ] `utils` 纯逻辑函数可用 `cargo test` 在纯终端环境跑通。
- [ ] 依赖方向符合 §4 图，无反向引用、无环。

---

## 9. 附则

- 本规划书与 `UI_SPEC.md` 互为补充：UI_SPEC 管"长得怎样/动得怎样"，本文件管"代码放哪里/谁依赖谁"。
- 若后续引入多窗口、后台任务、插件机制，应在 `app.rs` 与 `utils/` 之上再扩层，仍遵循单向依赖。
- 资源（图标/`.ui`）统一放 `resources/`，不散落在 `src/`。
